## Month 1 — Frontend Foundations

- **Debugging: consola primero, código después.** Cuando la UI no renderiza nada, el primer paso es mirar la pestaña Console de DevTools, no adivinar leyendo el código — React tira ahí el error exacto que rompió el render.
- **Pasar una función vs. llamarla.** `prop={handleEdit}` pasa la referencia a la función (se ejecuta cuando el hijo la invoque). `prop={handleEdit()}` la ejecuta *inmediatamente*, durante el render de `App` — con argumentos vacíos, y guarda el *resultado* (normalmente `undefined`) como prop. Bug real cometido y corregido: `handleEdit={handleEdit()}` en vez de `handleEdit={handleEdit}`.
- **Cómo React pasa las props.** Un componente recibe un único objeto con todas las props (`(props) => {...}`), no un objeto anidado bajo una key llamada `props` (`({ props }) => {...}` es incorrecto).
- **Colocar estado y lógica juntos.** El componente dueño del estado (`App`, que tiene `applications`, `company`, `editingId`, etc.) debe contener también la lógica que lo modifica (`handleEdit`, `handleDelete`). Los componentes hijos que no dueñan ese estado (`ApplicationList`) deben ser "tontos": reciben datos + callbacks ya armados y solo avisan *qué pasó* (ej. "se clickeó editar en el id X"), sin decidir *qué hacer* con esa información. Evita prop drilling de setters que no le corresponden al hijo.
- **`React.memo` compara props por referencia (shallow), no por valor.** Si *todas* las props mantienen la misma referencia entre renders, el componente se salta el render ("Did not render" en el Profiler). Si una sola prop cambia de referencia (aunque el contenido sea "igual"), memo no ayuda.
- **`useCallback` no evita re-renders por sí solo.** Solo le dice a React "devolveme la misma función de la vez anterior si las dependencias no cambiaron", en vez de crear una nueva en cada render. Es indispensable combinarlo con `React.memo` en el hijo cuando le pasás handlers como props — si no, memo nunca sirve porque los handlers son "props nuevas" en cada render del padre.
- **Stale closures.** Si el array de dependencias de `useCallback` (o `useEffect`) queda vacío `[]` pero la función usa una variable externa (ej. `applications`), la función queda "congelada" con el valor de esa variable tal como era en el render donde se creó — no ve actualizaciones futuras. Hay que declarar esa variable como dependencia para que React recree la función cuando cambie.
- **Cadena completa de optimización de re-renders (demostrada con el Profiler):** un solo componente monolítico re-renderiza todo al tipear → extraer un componente hijo no cambia nada sin memo → memo sin useCallback tampoco alcanza (props de función cambian de referencia) → memo + useCallback juntos sí evitan el render innecesario. Cada pieza depende de la anterior.
- **`useMemo` vs. `useCallback` — memorizan cosas distintas.** `useCallback` memoriza una *función* (misma referencia entre renders). `useMemo` memoriza el *resultado de un cálculo* (mismo valor calculado, sin recalcularlo, mientras las dependencias no cambien). Confusión real cometida: reachar por `useCallback` para derivar una lista filtrada, cuando lo que hace falta ahí es memorizar un *valor derivado* (`useMemo`), no una función.
- **El array de dependencias aplica a "cualquier variable externa usada adentro", no solo a la que disparó el cambio que te importa.** Bug real: `useMemo(() => applications.filter(...), [filterStatus])` — el cálculo usa `applications` *y* `filterStatus`, pero las deps solo tenían `filterStatus`. Resultado: al montar el componente, `applications` empieza vacío (`[]`); cuando el fetch trae los datos reales y `applications` cambia, `filterStatus` no cambió, así que React reusa el valor memoizado viejo (la lista vacía) — la lista queda vacía hasta que el usuario toca el filtro. Es el mismo patrón de stale closure ya visto con `useCallback` (sesión 2026-08-01): la regla general es "toda variable externa referenciada adentro va en las deps", sin importar si el hook es `useCallback`, `useMemo` o `useEffect`.
- **Filtrar en cliente vs. servidor — es una decisión de trade-off, no una regla fija.** El instinto de mandar el filtro al backend (evitar traer de más) es válido en general, pero para un dataset chico que ya está completo en memoria del front, la vuelta a la red por cada cambio de filtro cuesta más que filtrar localmente. La pregunta correcta es "¿cuántos datos se mueven y con qué frecuencia?", no una regla universal de "filtrar siempre en el servidor".
